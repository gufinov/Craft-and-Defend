# P3K — blueprints: castle pieces stamped from ordinary blocks

## Outcome

Owner decision 2026-09-18: castle pieces are blueprints that stamp ordinary blocks. Once built, the world holds plain voxels — removable, replaceable, mineable, and understood by pathfinding and breaching. Machines (ballista, catapult) remain entities. This slice delivers the data contract, the stamp engine, sockets, a first catalogue and diagnostics; the player-facing entry point (build wheel or B-menu page) is the next slice.

## Data contract

- `contracts/blueprints.json` (mirrored to `game/data/blueprints.json`) is generated by `python tools/generate_blueprints.py` and guarded by `tests/test_blueprints.py`.
- A blueprint: `id`, `display_name`, `size [x,y,z]`, `blocks` = `{offset:[x,y,z], block:<block id>}` relative to the footprint's minimum corner, `sockets` = `{id, type: top|side, offset}` on the footprint boundary, `note`.
- First catalogue: `foundation_4` (16 castle stone), `tower_segment_4` (36 castle stone ring, three courses, plus 3 stone spiral steps), `cap_4` / `cap_6` / `cap_8` (castle-stone edged plank floor with a crenellated one-course parapet; 8×8 has the 6×6 interior that seats a catapult and a ballista), `wall_4` (4×3 castle stone).
- Every block must be one an inventory item can place (`places_block`), because stamping consumes those items.

## Runtime contract

- `InteractionService.blueprints()` / `blueprint(id)` load the catalogue once. `blueprint_cells(id, anchor, quarters)` resolves rotated world cells with their voxel and item; `rotate_blueprint_offset` turns offsets about +y within the footprint.
- `begin_blueprint_at(id, anchor, quarters)` starts a plan in the same machinery as P3J drag building; `move_blueprint(anchor, quarters)` re-anchors; `update_drag_place` follows the aimed placement cell; `drag_state()` reports per-cell `ok` / `blocked` / `unaffordable` plus per-item `costs`; `commit_drag_place()` stamps; `cancel_drag_place()` discards.
- Planning is support-first as a fixpoint: cells whose only support would come later in the list are retried after the pass; what never gains support is blocked `UNSUPPORTED`. Per-block-type budgets trim only that type's cells. Commit writes every `ok` cell then runs one inventory transaction across all block types, rolling back on failure. Result `BLUEPRINT_STAMPED` with `cells`, `count`, `items`, `blueprint_id`.
- The drag/blueprint ghost textures each cell with the block it will become; amber = unaffordable, red = blocked.
- Sockets are data for stacking: the diagnostic stacks foundation → segment → cap by adding each piece's `top` socket offset. Socket-driven ghosting on look (Rust-style build-up) is the next slice.

## Acceptance

- T110 catalogue as the runtime sees it; wall rotation from x onto z.
- T111 foundation → segment → cap stacked through top sockets, costs across castle stone / stone / planks, exact inventory accounting, spiral steps present, interior clear.
- T112 cap_8 short of planks trims only plank cells, skips a pre-occupied cell, cancel builds nothing, then stamps every affordable cell.
- T113 rendered stamped tower and blueprint ghost.
- `python -m unittest discover -s tests` includes the catalogue guard.
