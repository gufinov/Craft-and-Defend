## Why the game would not start (verified, resolved)

`tools/start_game.ps1` refuses to launch unless `git status --porcelain -- game` is empty. The prior Codex session ran out of tokens mid-P3H.3 and left 17 modified plus 4 untracked files, seven of them under `game/`. The launcher therefore rebuilt successfully every time and then threw `provenance does not match the current clean game tree`, because the tree was still dirty after the rebuild. Every `TEST_*.cmd` calls the same script with `-PrepareOnly`, so the runtime test runners were blocked by the same condition.

Resolution: the P3H.3 work-in-progress was reviewed and committed as `3a05452` (`wip(p3h3)`). With a clean `game/` tree the launcher rebuilt once, the manifest `game_tree` matched `HEAD:game` (`cddb74a2…`), and `TEST_P3F_PRESENTATION.cmd` passed T90/T91/T92/T103/T104/T105/T106 on the exported build. The provenance guard itself was left unchanged; making it warn instead of throw on a dirty tree is an open proposal, not a decision (see Proposals).

## File ownership (verified, mitigated)

Every worktree `.git` file and most source files are owned by the Windows account `MYPCIE5\CodexSandboxOffline`, not `MYPCIE5\Tony`. Git refuses those directories from Tony's account ("dubious ownership"). Tony has Modify ACL rights, so this is git's safety check rather than a permission wall. The launcher already passes an inline `safe.directory`; ordinary git did not.

Mitigation: one global entry `safe.directory = D:/CODEX/Craft_and_Defend/*` was added to Tony's git config, matching the per-worktree pattern already used for every other `D:\CODEX` project. Taking ownership of the tree was not done; it is unnecessary for git use and is a broader machine change.

## Presentation positioning — root cause (verified by measurement)

Both reported defects (held-item placement and icon placement inside grid cells) share one cause: the art carries no positional metadata, so all positioning is fixed cell geometry plus hand-tuned constants.

`ItemIconCatalog` slices `assets/ui/item_atlas_p3h2.png` (1536×1024) into a 6×4 grid of 256 px cells with two special-cased row heights. Measured alpha bounding boxes (threshold α>128) against those cells:

| Rows | Measured | Visible effect |
|---|---|---|
| Row 3 (workbench … tower platform) | objects 5–16 px from the cell top, 42–50 px from the bottom | icons float high in their slot |
| Row 4 (gate frame … catapult) | 81–96 px of empty cell below each object; sword/axe occupy the top-left | icons sit high-left and look small |
| coal, iron ore, iron ingot, iron pick | drop shadow bleeds into the next row | faint smudge at the top of the neighbouring icon |

The atlas has no fully opaque pixel (maximum α = 254) and a haze of α 1–16 across roughly 23 % of the canvas, which is the origin of the earlier "baked card background" reports.

`HeldItemView` draws the same atlas cell as a flat `Sprite3D` in camera space, anchored at the cell centre and positioned by `TOOL_BASE_POSITION` / `LOW_BASE_POSITION`. Because a sword's grip is far from its cell centre, "handle seated at the screen base" can only be approximated by nudging constants, and every atlas regeneration moves it again. `window/stretch/aspect = "expand"` also shifts the apparent placement between 16:9 and ultrawide, which is why ultrawide re-tuning recurs. The rendered T104 evidence frame shows the grip clipped at the bottom edge and the blade sweeping flat across the hotbar during the swing.

Proposal (data, not tuning): add `assets/ui/item_atlas.json` with, per item, the tight alpha bounds and a grip/anchor point in atlas pixels. The catalog centres icons on true bounds; the held view pins the anchor instead of the sprite centre. Bounds can be generated from the PNG; anchors need one human mark per tool (about six items). Anchor data carries over unchanged if hands/arms or 3D equipment are added later.

## Combat and invasions

Current "battles" are one `BasicRaider` capsule following a `LocalGridPathfinder` route to a core after a fixed warning, which is faithful to the P3 navigation objective but is not a combat loop. Tony's stated direction is wave-based invasions in the manner of `D:\CODEX\MinionClash` (`docs/GAMEPLAY_CONTRACT.md` there: plain state as the sole authority with scenes as projections, lane pressure toward a core, mirrored waves, visible dodgeable projectiles, same-team queuing at merges). The transferable difference is that this terrain is editable voxels, so lanes are routes found through the navigation snapshot rather than authored splines, which the P2/P3 pathfinder already provides. A wave system here is: timed spawn of N raiders at field-side spawn points → each plans via the snapshot → attack obstruction or core → escalation. Consolidation of the three defense services (debt 2) is the prerequisite. This is a proposal for a future card, not an active commission.
